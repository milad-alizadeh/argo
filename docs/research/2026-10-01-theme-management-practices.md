# Theme management for the desktop cockpit

Research checked 2026-10-01. This note uses current primary documentation and a focused read of Argo's desktop theme paths. It recommends a contract for future token and theme work; it does not choose brand colors or change production code.

## Existing contract and implementation

- [Design stack](../design-stack.md) makes [`tokens.css`](../../apps/desktop/src/platform/renderer/tokens.css) the sole token contract. [`globals.css`](../../apps/desktop/src/platform/renderer/styles/globals.css) imports it and defines global styles. [ADR-0038](../adr/0038-the-desktop-cockpit-is-opaque.md) requires opaque surfaces, its background/card/muted/popover role ordering, and System (default), Light, and Dark appearances. A custom theme's values remain undecided. A branded theme should therefore fill these roles without changing their surface meaning or introducing translucent chrome.
- [`components.json`](../../apps/desktop/components.json) sets `base-nova`, neutral, `cssVariables: true`, and the generated UI path. Tailwind is `^4.3.3`, shadcn is `4.21.0`, and Electron is `44.2.0` in [`package.json`](../../apps/desktop/package.json). The current token file already maps shadcn roles, chart/sidebar roles, and radius names through `@theme inline`; `:root` and `.dark` supply values.
- The main process applies the saved appearance to `nativeTheme.themeSource` and sends its resolved `dark` value on native updates ([`appearance.ts`](../../apps/desktop/src/platform/main/appearance.ts), [`appearance.ts`](../../apps/desktop/src/platform/contract/appearance.ts)). The renderer expects `getAppearance` and `setAppearance`, but [`preload.ts`](../../apps/desktop/src/preload.ts#L77) exposes only `onAppearanceChanged`. [`use-appearance.ts`](../../apps/desktop/src/platform/renderer/use-appearance.ts#L33) returns before subscribing when the getter is absent, and its setter callback also returns when the setter is absent. Thus the production hook retains its initial `dark: true` rather than receiving the saved or System answer through this path. Storybook supplies mocked methods. This integration gap needs a validated initial-state transport and mutation operation before extending the theme model.
- The renderer has effects for `.dark` and `colorScheme`, but [`index.html`](../../apps/desktop/index.html) has no early appearance bootstrap or color-scheme metadata. Its light initial DOM and initial dark effect create a first-paint risk, not a visually reproduced flash. The absent getter means that a later saved-state answer does not currently arrive through this hook.
- The native window ground is hard-coded as `#ffffff`/`#0a0a0a` in the shared appearance contract, while the current CSS background resolves from neutral-100 in light and `#292c30` in dark. Electron paints that native ground before CSS. This is a source-level mismatch, not a measured flash. [`create-window.ts`](../../apps/desktop/src/platform/main/window/create-window.ts) sets it at creation and the watcher updates it later.

## How the CSS contract works

shadcn recommends semantic CSS variables and uses background/foreground pairs: the base role is the surface and its `-foreground` role is the text or icon placed on it. Its documented `bg-primary text-primary-foreground` example uses `--primary` and `--primary-foreground`. `components.json`'s `baseColor` generates the initial neutral tokens; `cssVariables: true` is an initialization choice, not a runtime theme selector. [shadcn theming](https://ui.shadcn.com/docs/theming), [components.json](https://ui.shadcn.com/docs/components-json).

Tailwind v4's `@theme` defines which utilities exist. `@theme inline` is appropriate when a utility must use a second, runtime-overridable variable; Tailwind documents that inline mode prevents unexpected resolution across CSS inheritance boundaries. Thus Argo's existing pattern means `bg-primary` reads the *current* `--primary`, while `text-primary-foreground` reads the current `--primary-foreground`:

```css
@theme inline {
  --color-primary: var(--primary);
  --color-primary-foreground: var(--primary-foreground);
}
:root { --primary: oklch(...); --primary-foreground: oklch(...); }
.dark { --primary: oklch(...); --primary-foreground: oklch(...); }
```

The emitted utilities are equivalent in intent to `background-color: var(--primary)` and `color: var(--primary-foreground)`, so changing the role values updates existing generated component classes. The same mapping is needed for background/foreground, card, popover, secondary, muted, accent, destructive, border/input/ring, chart 1-5, sidebar and its foreground/primary/accent/border/ring roles, and the radius scale. There is no reason to rewrite every component class when these roles change. [Tailwind theme variables](https://tailwindcss.com/docs/theme), [shadcn theming](https://ui.shadcn.com/docs/theming).

The Base UI or Radix layer supplies interaction primitives; the checked-in shadcn registry source supplies Tailwind classes that consume the CSS roles. shadcn explicitly supports either primitive implementation behind its component API. For this repo, keep the existing registry and change values at the token contract. This is an Argo proposal, not a shadcn requirement. [shadcn Base UI documentation](https://ui.shadcn.com/docs/changelog/2026-01-base-ui), [shadcn components.json](https://ui.shadcn.com/docs/components-json).

## Recommended state model

Keep **theme identity** (for example `default` or a future `argo`) separate from **appearance preference** (`system | light | dark`). Resolve `system` to light or dark from Electron; then select that theme's complete appearance values. This separation is a proposal for Argo. It preserves ADR-0038's three-way appearance choice and allows the default theme to remain available beside an optional branded theme. Electron documents exactly this `themeSource` state machine: `system` follows the OS, `light`/`dark` override native UI and Chromium's `prefers-color-scheme`, `shouldUseDarkColors` is the resolved value, and `updated` reports changes. [Electron nativeTheme](https://www.electronjs.org/docs/latest/api/native-theme).

Suggested resolved state: `{ themeId, appearance, dark }`, with one owner and one change event. The main process already applies stored appearance and owns native window color. Repair its absent renderer transport before extending the contract. At startup, validate stored identifiers at the storage boundary, report and count unknown values, and fall back to a known complete theme and `system`. At runtime, apply theme identity and resolved `.dark` to the document element in one update, notify JavaScript consumers using a change signal that includes both identity and dark, and update the native window background. A theme switch between two dark themes must still invalidate JS-rendered content. This is an inference from the current Argo contracts and the behavior of the consumers below.

Each selectable theme should define a complete light set and a complete dark set for every public role it changes. Shared values can inherit from the default theme, but review the **resolved** token matrix, including foreground pairs, focus ring, charts, sidebars, syntax colors, status colors, and window background. A partial CSS override is technically valid because custom properties inherit and cascade; accepting it as a theme silently couples the custom palette to later default-theme changes. Prefer explicit completeness checks for a shipped selectable theme. CSS inheritance is documented by [MDN custom properties](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Cascading_variables/Using_custom_properties); the completeness policy is an Argo proposal.

Keep theme selectors on `<html>`, not only under the React root. CSS custom properties inherit through the DOM, and a React portal may be physically mounted under `body` rather than its logical parent; a selector under `#root` would miss it. A scoped preview can instead place the full values on the preview host and send its popovers to a portal container inside that host. [MDN custom properties](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Cascading_variables/Using_custom_properties), [React createPortal](https://react.dev/reference/react-dom/createPortal).

For Tailwind `dark:*`, Argo already uses a `.dark` custom variant. Tailwind v4 documents that custom variant pattern and `matchMedia` for a three-way browser implementation. Electron's `nativeTheme` is the better authority here because it also aligns native menus, frames, and the CSS media query. [Tailwind dark mode](https://tailwindcss.com/docs/dark-mode), [Electron nativeTheme](https://www.electronjs.org/docs/latest/api/native-theme).

## First paint, native chrome, and accessibility

Electron recommends setting `BrowserWindow.backgroundColor` near the app background even when waiting for `ready-to-show`; it also provides `setBackgroundColor` for changes. The native color should be derived from or generated alongside the selected theme's resolved `--background` equivalent, not maintained as an unrelated value. For exact matching, resolve the selected theme before the first window is made and give Electron a color format its window API accepts. [Electron BrowserWindow](https://www.electronjs.org/docs/latest/api/browser-window/).

The renderer must apply the resolved selector before visible content is painted. Tailwind's web example puts its class-setting script in `<head>` to avoid a flash; in Argo, a small preload/bootstrap state or an initial state delivered before showing the window can serve that purpose under its CSP. This needs an implementation proof in packaged Electron: the present effect-based update alone cannot guarantee first paint. A `<meta name="color-scheme">` before CSS and the resolved root `color-scheme` inform browser-native controls and scrollbars, but do not replace the palette variables. [Tailwind dark mode](https://tailwindcss.com/docs/dark-mode), [MDN color-scheme meta](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/meta/name/color-scheme), [MDN color-scheme CSS](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/color-scheme).

Check each resolved text/ground pair in both appearances and interactive states. WCAG AA requires 4.5:1 for ordinary text and 3:1 for large text; meaningful control outlines and graphical objects require 3:1 against adjacent colors. Test actual composited colors where alpha or `color-mix()` is used. [W3C text contrast](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum), [W3C non-text contrast](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast). Forced-colors mode can replace author colors at paint time and removes box shadows, so retain semantic borders/focus indicators and make targeted forced-colors fixes rather than disabling it globally. Motion preferences are independent of theme identity; keep honoring reduced motion for nonessential transitions. [MDN forced-colors](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/%40media/forced-colors), [MDN reduced motion](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/%40media/prefers-reduced-motion).

## Non-CSS consumers

- **Mermaid:** Argo reads computed CSS values into a one-pixel canvas, converts them to sRGB, and sends `rgba(...)` strings to Mermaid's `base` theme ([`mermaid-theme.ts`](../../apps/desktop/src/domains/sessions/renderer/feed/content/mermaid-theme.ts)). Mermaid documents `base` as the customizable theme and hex-only color inputs. The current output format is therefore unsupported by that documentation, not proof of a rendered failure. Emit documented hex colors with an explicit alpha-compositing policy, or prove another supported format against the pinned library. [`FeedMermaid`](../../apps/desktop/src/domains/sessions/renderer/feed/content/feed-mermaid.tsx) currently redraws on `dark` but not theme identity; redraw on the full resolved theme key after the root values have changed. [Mermaid theming](https://mermaid.js.org/config/theming.html#color-and-color-calculation).
- **CodeMirror and Shiki:** The editor uses a CodeMirror theme extension with `var(--popover)` for background, but vendor Xcode syntax colors are still their own palette ([`project-setup-editor-theme.ts`](../../apps/desktop/src/domains/projects/renderer/onboarding/editor/project-setup-editor-theme.ts)). Shiki's Xcode theme registration uses CSS variable references ([`xcode-code-theme.ts`](../../apps/desktop/src/platform/renderer/components/xcode-code-theme.ts)). CSS variables in mounted styles can follow the cascade; an extension's *dark mode setting* or any captured JS color must still be reconfigured when resolved appearance changes. CodeMirror's official guide describes themes as extensions with a `{ dark: true }` option. [CodeMirror styling](https://codemirror.net/examples/styling/).
- **Canvas and generated SVG:** `getComputedStyle()` returns resolved, live styles for an element, but copied pixel colors and already-generated SVG markup are snapshots. Read colors again and redraw when `{themeId, dark}` changes. Read the computed style of the element that owns the token, which matters for a scoped preview or portal. This is an inference from [MDN getComputedStyle](https://developer.mozilla.org/en-US/docs/Web/API/Window/getComputedStyle) and the current Mermaid implementation.

## Limits and decisions left open

This is a source and code inspection, not a visual test, color audit, or benchmark. The selected brand palette, which extra Argo role colors belong to each theme, whether themes can be imported, and the exact early-state transport are product/implementation decisions. Current Electron, Tailwind, shadcn, React, Mermaid, CodeMirror, MDN, and W3C pages were checked on 2026-10-01; the repository versions and local contract should be rechecked when implementation begins.
