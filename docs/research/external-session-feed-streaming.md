# External Session Feed: how other tools stream it, and what vendor APIs allow

Researched 2026-10-01. Open source repos were cloned and read at the commit in each link. Closed products are judged from docs and issues. It builds on [agent-cockpit-prior-art.md](./agent-cockpit-prior-art.md), which covered status and listing. This file covers the conversation itself (the Feed).

Labels: **Confirmed** means a cited source says it or the cited code does it. **Unconfirmed** means inferred, second-hand, or not found.

Short names used below. `CCV` is claude-code-viewer. `LoS` is Line of Sight. Shas: codex `60947e2`, CCV `9367cf0`, claude-code-trace `833971e`, codex-trace `6b21dad`, cc-sessions-viewer `c81f592`, LoS `dc04379`, VibeDeck `786d874`, CloudCLI `dc7cb6c`, Opcode `d1ca30a`, vscode-copilot-chat `5863f5a` (repo head is dated 2026-05-20).

## Q1. Full Feed or summary? Live or on open?

Answer: every tool that shows an external Session's conversation shows the full Feed, and all but Opcode update it live. The summary-only tools (agentsctl, hook hosts, cmux) never show the conversation.

- Confirmed: CCV refetches the session and renders every entry type, including unparseable lines as an `x-error` row ([parseJsonl.ts#L4-L36](https://github.com/d-kimuson/claude-code-viewer/blob/9367cf006be9965c954e6cd36526f2195dce67ea/src/server/core/claude-code/functions/parseJsonl.ts#L4-L36)). Its README says "You can start a Claude Code session from the CLI ... and watch it live" ([README L20](https://github.com/d-kimuson/claude-code-viewer/blob/9367cf006be9965c954e6cd36526f2195dce67ea/README.md?plain=1#L20)).
- Confirmed: LoS says it "shows every past and live session" and reads the JSONL "both CLIs already keep on disk" ([README](https://github.com/twinwest/line-of-sight/blob/dc04379f2f8ca65c5f501e56d7efe5b3d8c6a8b1/README.md)).
- Confirmed: Opcode `load_session_history` reads the file once on open ([claude.rs#L882-L907](https://github.com/winfunc/opcode/blob/d1ca30a3c0c39fff01fde2f86c2d5af6a1db658b/src-tauri/src/commands/claude.rs#L882-L907)). Live streaming there is only for runs it spawns (same file, L919 to L1008).
- Confirmed: CloudCLI reloads the open session on a watcher tick. The hook that does it is [useChatSessionState.ts#L815-L842](https://github.com/siteboon/claudecodeui/blob/dc7cb6c6dcd22988f3241e10303298046ead351e/src/modules/chat/hooks/useChatSessionState.ts#L815-L842). It skips the reload while the UI itself is streaming.
- Confirmed: claude-code-trace computes an "ongoing" flag from the transcript, so it can tell a running Session from an idle one ([watcher.rs#L204-L243](https://github.com/delexw/claude-code-trace/blob/833971e0badb8189ae8d1639490f75938a32bbcd/src-tauri/src/watcher.rs#L204-L243)).
- Confirmed: Claude agent view shows a peek, not the transcript. Quote: peek shows "A working session: its full status sentence" and only backgrounded sessions can be attached ([agent view docs](https://code.claude.com/docs/en/agent-view)).
- Unconfirmed: whether VS Code refreshes an open external Claude Session. No file watcher exists in `src/extension/chatSessions/claude` (grep of the clone). The prior survey says VS Code scans disk once at startup ([#335215](https://github.com/microsoft/vscode/issues/335215)).
- Unconfirmed: what the Codex desktop app does for a CLI thread still running. Issue [#24197](https://github.com/openai/codex/issues/24197) only covers listing and reading finished CLI threads.
- Dead end: cmux's Codex transcript monitor only builds a `Stop` hook payload from a rollout ([CodexTranscriptMonitorStopReplay.swift#L1-L48](https://github.com/manaflow-ai/cmux/blob/b520727d0c1905fa921b55f73af261e586c644b3/CLI/CodexTranscriptMonitorStopReplay.swift#L1-L48)). It renders no Feed.

## Q2. How do they get the conversation and live updates?

Answer: dominant pattern is watch the file, then re-read and re-parse it. Nobody in the set attaches to the process. Only VS Code calls a vendor API for history, and it does not use one for live.

**File watch, then full re-parse (most tools)**
- Confirmed, CCV: recursive `fs.watch` on the projects dir ([fileWatcher.ts#L126](https://github.com/d-kimuson/claude-code-viewer/blob/9367cf006be9965c954e6cd36526f2195dce67ea/src/server/core/events/services/fileWatcher.ts#L126)), 100 ms debounce per session ([L75](https://github.com/d-kimuson/claude-code-viewer/blob/9367cf006be9965c954e6cd36526f2195dce67ea/src/server/core/events/services/fileWatcher.ts#L75)). The server then reads the whole file with `readFileString` ([SessionRepository.ts#L46](https://github.com/d-kimuson/claude-code-viewer/blob/9367cf006be9965c954e6cd36526f2195dce67ea/src/server/core/session/infrastructure/SessionRepository.ts#L46)). The client invalidates its query on `sessionChanged` ([SSEEventListeners.tsx#L25-L29](https://github.com/d-kimuson/claude-code-viewer/blob/9367cf006be9965c954e6cd36526f2195dce67ea/src/web/app/components/SSEEventListeners.tsx#L25-L29)).
- Confirmed, claude-code-trace and codex-trace: `RecommendedWatcher` on the project dir ([watcher.rs#L123](https://github.com/delexw/claude-code-trace/blob/833971e0badb8189ae8d1639490f75938a32bbcd/src-tauri/src/watcher.rs#L123)), 1000 ms debounce ([L29](https://github.com/delexw/claude-code-trace/blob/833971e0badb8189ae8d1639490f75938a32bbcd/src-tauri/src/watcher.rs#L29)). The comment at L204 says the view is rebuilt "from scratch on every event" to avoid multi-GB memory growth. It also resets on file truncation after `/clear`. codex-trace has the same file ([L11](https://github.com/PixelPaw-Labs/codex-trace/blob/6b21dad4b872aa609188fce9994a2dc371b8cc30/src-tauri/src/watcher.rs#L11)).
- Confirmed, cc-sessions-viewer: the author explains the choice in the file header. The parser has cross-line state (queued user messages, tool result pairing), so an incremental parser "would need a rewrite". It re-reads the whole file, watches the parent dir because agents replace files atomically, and adds three gates: 200 ms debounce, 1500 ms poll fallback, 400 ms minimum gap between re-parses, because one Codex rollout is 160 MB ([watch.rs#L1-L36](https://github.com/jerrywu001/cc-sessions-viewer/blob/c81f59223af22893d2d5da5c77d3b2c3af0a20a3/src-tauri/src/watch.rs#L1-L36), [L165-L175](https://github.com/jerrywu001/cc-sessions-viewer/blob/c81f59223af22893d2d5da5c77d3b2c3af0a20a3/src-tauri/src/watch.rs#L165-L175)).
- Confirmed, CloudCLI: chokidar with `usePolling: true`, `interval: 6_000` ([sessions-watcher.service.ts#L211-L220](https://github.com/siteboon/claudecodeui/blob/dc7cb6c6dcd22988f3241e10303298046ead351e/server/modules/providers/services/sessions-watcher.service.ts#L211-L220)), flush debounce 500 ms ([L44](https://github.com/siteboon/claudecodeui/blob/dc7cb6c6dcd22988f3241e10303298046ead351e/server/modules/providers/services/sessions-watcher.service.ts#L44)). The prior survey said 6 s. This adds that polling is forced.

**File watch, then incremental tail (minority)**
- Confirmed, LoS: chokidar ([ingest.ts#L65](https://github.com/twinwest/line-of-sight/blob/dc04379f2f8ca65c5f501e56d7efe5b3d8c6a8b1/src/daemon/ingest.ts#L65)), saved `byteOffset` per session, re-parse from zero if the file shrank ([L228-L232](https://github.com/twinwest/line-of-sight/blob/dc04379f2f8ca65c5f501e56d7efe5b3d8c6a8b1/src/daemon/ingest.ts#L228-L232)). It accepts `rollout-*.jsonl.zst`, so it reads compressed Codex rollouts ([codex.ts#L21](https://github.com/twinwest/line-of-sight/blob/dc04379f2f8ca65c5f501e56d7efe5b3d8c6a8b1/src/adapters/codex.ts#L21)).
- Confirmed, VibeDeck: `watchfiles.awatch` ([server.py#L1184](https://github.com/tijszwinkels/VibeDeck/blob/786d8742694ae2eafd7be233da626c6ecf4f3728/src/vibedeck/server.py#L1184)). Its tailer splits content into complete lines and keeps a partial last line in a buffer ([base.py#L57-L73](https://github.com/tijszwinkels/VibeDeck/blob/786d8742694ae2eafd7be233da626c6ecf4f3728/src/vibedeck/backends/base.py#L57-L73)). The Claude tailer keeps only `user` and `assistant` entries ([tailer.py#L29](https://github.com/tijszwinkels/VibeDeck/blob/786d8742694ae2eafd7be233da626c6ecf4f3728/src/vibedeck/backends/claude_code/tailer.py#L29)).
- Confirmed, Agent Monitor: byte cursors for Codex, hooks for Claude ([codex-ingest.js#L6](https://github.com/hoangsonww/Claude-Code-Agent-Monitor/blob/fc4d1cbf2e4a5b5e6eee1ce5acd06d29077fe87b/server/lib/codex-ingest.js#L6), [README L118](https://github.com/hoangsonww/Claude-Code-Agent-Monitor/blob/fc4d1cbf2e4a5b5e6eee1ce5acd06d29077fe87b/README.md?plain=1#L118)). Its Codex app-server client only starts runs ([codex-app-server.js#L1-L5](https://github.com/hoangsonww/Claude-Code-Agent-Monitor/blob/fc4d1cbf2e4a5b5e6eee1ce5acd06d29077fe87b/server/lib/codex-app-server.js#L1-L5)).

**Vendor API for history**
- Confirmed, VS Code: "without any JSONL parsing" for the main chain, via `listSessions`, `getSessionInfo`, `getSessionMessages` ([sdkSessionAdapter.ts#L7-L19](https://github.com/microsoft/vscode-copilot-chat/blob/5863f5a7088958050792b5dccbe8b46c6e13eccc/src/extension/chatSessions/claude/node/sessionParser/sdkSessionAdapter.ts#L7-L19), [claudeCodeSdkService.ts#L94-L96](https://github.com/microsoft/vscode-copilot-chat/blob/5863f5a7088958050792b5dccbe8b46c6e13eccc/src/extension/chatSessions/claude/node/claudeCodeSdkService.ts#L94-L96)). It still reads raw JSONL for subagents because the SDK "strips" `toolUseResult.agentId` ([L103](https://github.com/microsoft/vscode-copilot-chat/blob/5863f5a7088958050792b5dccbe8b46c6e13eccc/src/extension/chatSessions/claude/node/sessionParser/sdkSessionAdapter.ts#L103), [service header](https://github.com/microsoft/vscode-copilot-chat/blob/5863f5a7088958050792b5dccbe8b46c6e13eccc/src/extension/chatSessions/claude/node/sessionParser/claudeCodeSessionService.ts#L8-L13)). The SDK docs now list `listSubagents` and `getSubagentMessages` ([session storage](https://code.claude.com/docs/en/agent-sdk/session-storage)). Whether they close that gap was not tested.
- Confirmed: in the clones I read (CCV, CloudCLI, LoS, claude-code-trace), none calls SDK `getSessionMessages`. CloudCLI has its own function of that name ([claude-sessions.provider.ts#L691](https://github.com/siteboon/claudecodeui/blob/dc7cb6c6dcd22988f3241e10303298046ead351e/server/modules/providers/list/claude/claude-sessions.provider.ts#L691)). Other repos were not searched.
- Confirmed, Codex TUI: `codex resume` reads through the app-server, not the file ([resume_picker_transcript_preview.rs#L38](https://github.com/openai/codex/blob/60947e234156ac12bdb7fba2477d3965f166bd34/codex-rs/tui/src/resume_picker_transcript_preview.rs#L38), [app_server_session.rs#L1145](https://github.com/openai/codex/blob/60947e234156ac12bdb7fba2477d3965f166bd34/codex-rs/tui/src/app_server_session.rs#L1145)).
- Not used by any tool found: tmux or pty capture for external Sessions. Those appear only where the tool owns the terminal (prior survey).

## Q3. Can a client subscribe to a Session running in another process?

Answer: no, for both vendors, with one Codex exception. Neither vendor offers a public stream of another process's Session. Codex lets many clients share one app-server daemon, but a Session started in a plain terminal TUI runs in its own embedded server.

**Codex**
- Confirmed: `thread/read` is a snapshot and does not subscribe. Docs: "Use `thread/read` when you want stored thread data but don't want to resume the thread or subscribe to its events." And `thread/turns/list`: "Use it to page a stored thread's turn history without resuming it." ([app-server docs](https://learn.chatgpt.com/docs/app-server)). Method table: [common.rs#L852-L868](https://github.com/openai/codex/blob/60947e234156ac12bdb7fba2477d3965f166bd34/codex-rs/app-server-protocol/src/protocol/common.rs#L852-L868). A comment there calls `thread/turns/list` and `thread/items/list` reads of "append-only rollout storage".
- Confirmed: `thread/resume` only finds a "running" thread inside its own `thread_manager` ([thread_processor.rs#L4281-L4321](https://github.com/openai/codex/blob/60947e234156ac12bdb7fba2477d3965f166bd34/codex-rs/app-server/src/request_processors/thread_processor.rs#L4281-L4321)). Otherwise it does a cold resume, which must take the writer lock: [live_writer.rs#L41-L46](https://github.com/openai/codex/blob/60947e234156ac12bdb7fba2477d3965f166bd34/codex-rs/thread-store/src/local/live_writer.rs#L41-L46). A lock held by another process returns `Conflict` ([mod.rs#L340-L353](https://github.com/openai/codex/blob/60947e234156ac12bdb7fba2477d3965f166bd34/codex-rs/thread-store/src/local/mod.rs#L340-L353)). The lock is an OS file lock under `thread-writer-locks/` ([writer_lock.rs#L1-L60](https://github.com/openai/codex/blob/60947e234156ac12bdb7fba2477d3965f166bd34/codex-rs/rollout/src/writer_lock.rs#L1-L60)).
- Confirmed from users: the failure is seen in practice as `thread <id> already has an active writer (code -32600)`. [#45406](https://github.com/openai/codex/issues/45406) (CLI `exec resume` blocked by the VS Code panel), [#46936](https://github.com/openai/codex/issues/46936) (a live thread shows "open in another app" with "no read-only history"; the reporter confirmed the old server "was still appending to the rollout"), [#37967](https://github.com/openai/codex/issues/37967) (iOS Remote opens finished threads but "in-progress ones fail"; a commenter ties it to the writer lock). All open, no OpenAI fix seen.
- Confirmed, a trap for readers: `thread/read` on a thread this server has not loaded returns the persisted turns, then marks any `InProgress` turn as `Interrupted`, because status is `notLoaded` ([thread_processor.rs#L2879-L2926](https://github.com/openai/codex/blob/60947e234156ac12bdb7fba2477d3965f166bd34/codex-rs/app-server/src/request_processors/thread_processor.rs#L2879-L2926), [thread_lifecycle.rs#L919-L933](https://github.com/openai/codex/blob/60947e234156ac12bdb7fba2477d3965f166bd34/codex-rs/app-server/src/request_processors/thread_lifecycle.rs#L919-L933)). A client of a second app-server would see a running external turn as interrupted.
- Confirmed: clients on the same daemon can subscribe. `thread/unsubscribe` "removes the current connection's subscription" ([docs](https://learn.chatgpt.com/docs/app-server)). Issue [#35676](https://github.com/openai/codex/issues/35676) describes an observer connected to the managed daemon beside a TUI. The daemon README says a TUI falls back to "an embedded server instead" if it cannot connect ([README#L24-L28](https://github.com/openai/codex/blob/60947e234156ac12bdb7fba2477d3965f166bd34/codex-rs/app-server-daemon/README.md?plain=1#L24-L28)). So a terminal TUI is not reliably on the shared daemon. The daemon README calls itself experimental.
- Confirmed: the protocol has `fs/watch` with `fs/changed` notifications, debounced 200 ms ([common.rs#L1013](https://github.com/openai/codex/blob/60947e234156ac12bdb7fba2477d3965f166bd34/codex-rs/app-server-protocol/src/protocol/common.rs#L1013), [fs_watch.rs#L27](https://github.com/openai/codex/blob/60947e234156ac12bdb7fba2477d3965f166bd34/codex-rs/app-server/src/fs_watch.rs#L27)). It is a file watcher, so it only moves the "watch the rollout" step behind the vendor API. Whether it is stable was not checked.
- Unconfirmed: no open issue found that asks for a read-only "follow another process's turn" subscription by name. [#35676](https://github.com/openai/codex/issues/35676) (presence), [#47193](https://github.com/openai/codex/issues/47193) (inject a message) and [#46936](https://github.com/openai/codex/issues/46936) (read-only history) come closest.

**Claude**
- Confirmed: SDK readers are disk snapshots. The TypeScript reference lists `getSessionMessages(sessionId, { dir, limit, offset })` and no subscribe or tail call ([reference](https://code.claude.com/docs/en/agent-sdk/typescript)). The sessions page shows it as a tool for "transcript viewers" ([sessions](https://code.claude.com/docs/en/agent-sdk/sessions)). Whether a mid-turn call returns the newest lines was not tested.
- Confirmed: `SessionStore.append` is called "after each batch of transcript entries is written locally" by the SDK that runs the query ([session storage](https://code.claude.com/docs/en/agent-sdk/session-storage)). It mirrors sessions the SDK runs. A terminal Session is not covered.
- Confirmed: the peer socket is inbound only. Docs: each session binds an inbox socket "where other sessions on the machine deliver messages" and the path is in `/status` and `CLAUDE_CODE_MESSAGING_SOCKET`. A sender can ask for "one notice when that session next goes idle or exits" with `notify_when_idle` (Claude Code v2.1.236 or later) ([cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging)). There is no read stream. Any message sent this way becomes a user turn, so it is not a safe probe.
- Confirmed, third party: `~/.claude/sessions/<pid>.json` holds `messagingSocketPath`, `status`, `waitingFor`, `updatedAt`. The wire format (`msgV: 1`, an auth frame) is "an implementation contract, not a stable public API" ([peer-message protocol notes](https://github.com/daymade/claude-code-skills/blob/main/peer-message/references/protocol-and-discovery.md)). The same notes say the registry is "best-effort, not a census".
- Confirmed: `claude agents` attach works for background sessions only ([agent view](https://code.claude.com/docs/en/agent-view)). Resuming the same session in a second terminal does not sync. Docs: "messages from both interleave into one transcript" ([sessions](https://code.claude.com/docs/en/sessions)).
- Confirmed: Remote Control keeps "the conversation ... in sync across all connected devices", but only to claude.ai and the Claude app ([docs](https://code.claude.com/docs/en/remote-control)). Unconfirmed: any API for a third-party client to attach. None is documented on that page.
- Confirmed: hooks give `transcript_path` to each hook ([sessions docs](https://code.claude.com/docs/en/sessions)), so a hook can say "the file changed". It only covers Sessions that had the hook when they started (prior survey, issue [#94620](https://github.com/anthropics/claude-code/issues/94620)).

## Q4. What decoding do these tools own?

Answer: every JSONL reader owns its decoder. None uses vendor types for transcript lines. They cope with format drift by validating at the edge, keeping unknown lines visible, and pinning fixtures. Only the Codex app-server path (and the Claude SDK chain) gives vendor-decoded data.

- Claude says the format is unstable. Quote: "The entry format is internal to Claude Code and changes between versions, so scripts that parse these files directly can break on any release" ([sessions docs](https://code.claude.com/docs/en/sessions)). Confirmed.
- CCV: a Zod union of 17 entry schemas ([index.ts#L20-L38](https://github.com/d-kimuson/claude-code-viewer/blob/9367cf006be9965c954e6cd36526f2195dce67ea/src/lib/conversation-schema/index.ts#L20-L38)). A line that fails JSON or schema becomes an `x-error` row with its line number, so it is shown and not lost (parseJsonl.ts L14-L33). Schema tests and a `mock-global-claude-dir` fixture tree exist. It pins `@anthropic-ai/claude-code` 2.1.220 in `package.json`. Confirmed.
- VS Code: a validator layer ("No Type Assertions") with lenient ids, but messages that fail validation are "silently skipped" ([README](https://github.com/microsoft/vscode-copilot-chat/blob/5863f5a7088958050792b5dccbe8b46c6e13eccc/src/extension/chatSessions/claude/node/sessionParser/README.md), [sdkSessionAdapter.ts#L114](https://github.com/microsoft/vscode-copilot-chat/blob/5863f5a7088958050792b5dccbe8b46c6e13eccc/src/extension/chatSessions/claude/node/sessionParser/sdkSessionAdapter.ts#L114)). ## What this means for Argo

These are readings of the evidence, not findings.

1. The pattern Argo uses (watch the file, decode it) is the norm. Six tools do it and ship. Dropping it is not supported by any vendor API today.
2. Full re-parse per event is common but has to be throttled (cc-sessions-viewer's three gates, claude-code-trace's 1 s). Argo's incremental offset read, with a shrink reset, matches LoS and is the cheaper design.
3. For history, a vendor reader is an option on both sides. Claude: `getSessionMessages` (user and assistant chain, raw `message`, subagents need other calls). Codex: `thread/read` or `thread/turns/list` through an app-server Argo runs. It is read-only, it does not take the writer lock, and it reads compressed rollouts. But it rewrites a running external turn to `Interrupted`, so Argo would need the file or the writer-lock check to know a turn is live.
4. `thread/resume` is wrong for external Codex Sessions. It fails with "active writer", and if it succeeded it would make Argo a second writer.
5. Use `fs/watch` or a plain watcher only as a trigger. Re-read through the decoder after it fires.
6. To watch for drift: Claude docs say the format changes per release, and Codex storage is moving (compression, paginated history). Keep fixtures per vendor version and show unknown lines, as CCV and LoS do.
