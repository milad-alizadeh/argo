# Token architecture and style reuse for the desktop cockpit

2026-10-01. Research for a token and theme architecture decision. This note reports what current primary sources support, then gives Argo-specific recommendations. It does not change the token contract.

## Local contract and decision boundary

Argo's desktop renderer uses Tailwind 4.3.3 and shadcn `base-nova` with `cssVariables: true` (`apps/desktop/package.json`, `apps/desktop/components.json`, `bun.lock`). `docs/design-stack.md` puts every shared token in `apps/desktop/src/platform/renderer/tokens.css`: `:root` supplies light values, `.dark` supplies dark overrides, and `globals.css` imports the contract. `apps/desktop/AGENTS.md` requires role names, typography roles for visible text, and tokenized color in both appearances. The current file already combines Tailwind `@theme` / `@theme inline` declarations, shadcn semantic colors, and app-specific measurements and colors. These are repository facts, not claims that every declaration is currently used or sound.

ADR-0038 fixes the surface hierarchy: opaque grounds, hairline seams, and shadows only for unanchored overlays. It maps the old Swift ideas to shadcn roles (`background`, `card`, `muted`, `popover`) without porting graphite values. A new architecture should preserve those decisions. In particular, adding a fifth general surface role or using component token names to evade the shadow rule would require a new design decision (`docs/adr/0038-the-desktop-cockpit-is-opaque.md`).

## What the sources establish

### Format and layers

The Design Tokens Community Group's 2025.10 format and resolver reports are **stable Community Group reports** dated 2025-10-28. They are not W3C Standards or W3C Recommendations. The format defines JSON tokens with `$value` and explicit or inherited `$type`, aliases, groups, and deprecation metadata. The resolver describes ordered sets and conditional modifiers, including light/dark contexts. It requires error reporting for unresolved or circular references. This is a useful interoperability format, not a mandate to move a CSS application to JSON. [DTCG reports index](https://www.designtokens.org/technical-reports/), [format](https://www.designtokens.org/TR/2025.10/format/), [resolver](https://www.designtokens.org/TR/2025.10/resolver/).

The mature systems use related, but not identical, layers. Material Web describes **reference** tokens as concrete values, **system** tokens as roles, and **component** tokens as attributes of a particular component; its component tokens can reference system tokens or have concrete values. Spectrum 2 describes primitives, semantic intent, and component-specific tokens used when no semantic decision fits. Carbon documents core, layering, and component color tokens. Atlassian asks consumers to choose a token for its meaning rather than because its present color matches. None of these sources establishes a universal count of tokens, a universal number of layers, or an obligation to introduce all layers in a small product. [Material Web theming](https://github.com/material-components/material-web/blob/main/docs/theming/README.md), [Spectrum token concepts, 2026-07-10](https://opensource.adobe.com/spectrum-design-data/articles/understanding-spectrum-tokens/), [Carbon color](https://www.carbondesignsystem.com/building-blocks/foundations/color/overview), [Atlassian token overview](https://atlassian.design/foundations/tokens/design-tokens/).

**Argo inference:** Keep a small shared semantic layer as the public contract. A raw palette is useful only where multiple independent semantic roles need the same adjustable source or external tooling needs a palette; an alias with no independent intent adds indirection. Permit a component token when the value belongs to that component's behavior or geometry and no shared role expresses it. A role may equal another role today and still deserve its own name if the two could reasonably diverge in a future theme. Conversely, two names for one intent create false choice even when their values differ by accident. Review equality by *meaning across themes and states*, not by comparing current hex or pixel values.

### CSS and Tailwind resolution

Tailwind v4 `@theme` variables both define CSS variables and determine which utilities exist. The namespace is functional: `--color-*` creates color utilities, `--text-*` creates font-size utilities, `--spacing-*` creates spacing and sizing utilities, and so on. A plain `:root` variable does not create a utility. Tailwind says `@theme inline` should be used when a theme variable references another variable so the generated utility uses the referenced variable at the element where it is applied. `--color-*: initial` resets the entire default color namespace; `--*: initial` resets the whole default theme. Tailwind's `static` option emits even unused variables; ordinary output only emits used theme variables. These are compiler controls and should not be used as a token-cleanup shortcut without checking affected utilities. [Tailwind theme variables](https://tailwindcss.com/docs/theme).

CSS custom properties inherit by default, and `var()` substitution happens at computed-value time. A missing or type-invalid value can make the consuming declaration invalid; an earlier declaration of the same property is not necessarily a fallback. `@property` can declare syntax, inheritance, and an initial value, but does not replace a theme-completeness check. [MDN custom properties](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Cascading_variables/Using_custom_properties), [MDN `var()`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/var), [MDN registered properties](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Properties_and_values_API/Registering_properties).

shadcn recommends CSS variables for themes, with semantic names such as `background`, `foreground`, and `primary`; its generated utilities map to those names. Its Tailwind v4 guide shows `:root` and `.dark` supplying appearance values and `@theme inline` exposing them to utilities and to JavaScript as CSS variables. This matches Argo's current toolchain. [shadcn theming](https://ui.shadcn.com/docs/theming), [shadcn Tailwind v4](https://ui.shadcn.com/docs/tailwind-v4).

**Argo inference:** Use `:root` and `.dark` for values that change with appearance, expose only utility-facing names through `@theme inline`, and keep stable non-utility variables as ordinary custom properties unless a Tailwind utility is actually needed. The key invariant is that every appearance supplies every appearance-sensitive role, including hover, selected, disabled, focus, and paired foreground/background roles. A token defined only in light mode can inherit its light value under `.dark`; CSS does not know that this is a design error.

### Theme completeness and contrast

Atlassian defines a theme as a collection of values for the same token names and gives light, dark, and high-contrast as examples. Material Web describes paired `on-*` content roles for key color roles and says the application decides how dark mode is activated. Spectrum Web Components changes underlying values while keeping token names stable, and its theme can vary color and scale independently. These are concrete examples of stable role names with conditional values, not evidence that Argo needs every mode those systems expose. [Atlassian token overview](https://atlassian.design/foundations/tokens/design-tokens/), [Material Web color](https://github.com/material-components/material-web/blob/main/docs/theming/color.md), [Material Web support](https://github.com/material-components/material-web/blob/main/docs/support.md), [Spectrum theme API](https://opensource.adobe.com/spectrum-web-components/tools/theme/api/).

**Argo inference:** Specify a finite theme matrix: light and dark for every semantic color; System selects one of them rather than becoming a third value set. Check foreground/background pairs in each row and interactive states on the surface where they actually render. Keep contrast decisions at the role pair, not solely at raw swatch level. If a future high-contrast or density setting is approved, add it as a separate axis where possible; do not hide a mode-specific override in one component's stylesheet.

### Families beyond color

The DTCG format defines typed values for dimensions, font families, font weights, durations, cubic Bézier curves, shadows, and composite typography or transition values. That provides a transport vocabulary; it does not specify Argo's scale or motion policy. Material Web's system tier includes typography, shape, and elevation, while Spectrum's semantic layer includes spacing and component geometry. Atlassian explicitly includes elevation and spacing among tokenized decisions. [DTCG format](https://www.designtokens.org/TR/2025.10/format/), [Material Web theming](https://github.com/material-components/material-web/blob/main/docs/theming/README.md), [Spectrum token concepts, 2026-07-10](https://opensource.adobe.com/spectrum-design-data/articles/understanding-spectrum-tokens/), [Atlassian token overview](https://atlassian.design/foundations/tokens/design-tokens/).

**Argo inference:** Keep one small set of reader text roles (size, line height, weight, tracking), a small spacing vocabulary for repeated layout relationships, and named duration/easing roles for repeated interactions. Tokenize a dimension when it represents a repeatable design decision or a cross-component alignment dependency, not merely because a CSS length exists. Local geometry such as one menu's width can stay component-local and named. Elevation tokens must obey ADR-0038: reusable overlay shadow, no shadow for anchored surfaces. A `--shadow-*` utility being available is not permission to apply it everywhere.

### Reuse, ownership, and change

Spectrum's component-specific tier is explicitly for decisions that cannot be expressed by a semantic token. Its Web Components contributor guide separates core component structure, theme override, and implementation-specific CSS. Atlassian's token guidance warns that color equality is not enough to choose a token, and it provides lint rules and migration tooling for adoption. DTCG has `$deprecated` metadata for tokens and groups, but a CSS-only application must document replacement and remove usages through its own process. [Spectrum token concepts, 2026-07-10](https://opensource.adobe.com/spectrum-design-data/articles/understanding-spectrum-tokens/), [Spectrum component styling](https://opensource.adobe.com/spectrum-web-components/guides/styling-components/), [Atlassian token overview](https://atlassian.design/foundations/tokens/design-tokens/), [Atlassian use in code](https://atlassian.design/foundations/tokens/use-tokens-in-code), [DTCG format](https://www.designtokens.org/TR/2025.10/format/).

**Argo inference:** Reuse a token when the visual decision is shared; reuse a CSS recipe when several owners need the same combination of tokens and states; reuse a React component when the same behavior and accessibility contract recur. Similar values alone do not earn a shared component. A shared recipe or component should have one owner and a reason to change together. If one use case needs a variant, name the variant for behavior or role. Repeated one-off overrides are evidence to reconsider the shared contract. For a rename, add a replacement, migrate readers, then remove the old name in a reviewed change; avoid permanent aliases that leave two public spellings. A documented deprecation period is warranted only when independently released consumers need it.

### CSS and JavaScript consumers

Tailwind exposes generated CSS variables for direct `var()` use; shadcn's v4 guide shows chart configuration reading those variables from JavaScript. Atlassian's JavaScript token helper depends on mounting its theme CSS, which shows that a JavaScript token name alone is not a runtime theme. Spectrum Web Components likewise exposes scoped CSS variables for components and application CSS. [Tailwind theme variables](https://tailwindcss.com/docs/theme), [shadcn Tailwind v4](https://ui.shadcn.com/docs/tailwind-v4), [Atlassian use in code](https://atlassian.design/foundations/tokens/use-tokens-in-code), [Spectrum theme API](https://opensource.adobe.com/spectrum-web-components/tools/theme/api/).

**Argo inference:** For rendered colors in canvas, charts, or a JS style prop, use the same semantic CSS variable the DOM uses; resolve its computed value at the boundary if an API requires a concrete color. Keep nonvisual state in TypeScript. Avoid a manually mirrored TypeScript color table: it can drift from `.dark` and from cascade scope. A generated typed token-name list could help if JS references become numerous, but that is a tooling need to prove, not an automatic second source of truth.

## Source-of-truth options for Argo

| Option | What it gains | Cost and fit now |
| --- | --- | --- |
| CSS first (`tokens.css`) | Native runtime cascade, direct Tailwind `@theme` mapping, shadcn's expected theme variables, no translation step. [Tailwind](https://tailwindcss.com/docs/theme), [shadcn](https://ui.shadcn.com/docs/theming). | Weak type checking for `var()` and no built-in completeness check. Fits one Electron renderer and the existing contract best. |
| DTCG JSON plus generation | A typed, tool-neutral exchange format, alias validation, and explicit light/dark resolution. [DTCG format](https://www.designtokens.org/TR/2025.10/format/), [resolver](https://www.designtokens.org/TR/2025.10/resolver/). | Needs a converter to preserve Tailwind namespaces, shadcn roles, CSS scoping, and any CSS expressions; generated CSS would become the runtime artifact. Fits when a real second consumer or design-tool exchange is required. |
| TypeScript first plus CSS generation | Compile-time authoring and programmatic transforms. This is an engineering possibility, not a requirement of the cited systems. | Needs a custom schema/generator and emitted CSS for the actual renderer; JS evaluation does not model CSS cascade by itself. No current cross-platform need justifies that extra contract. |

**Recommendation:** Keep CSS first for this ticket. Tighten naming, theme coverage, and token ownership within the existing file. Treat DTCG 2025.10 as an interchange target if Argo later needs to feed Figma or a second platform from one source. Do not introduce JSON or TypeScript generation just to make today's CSS look architecturally elaborate. This is an Argo-specific judgment from the current one-renderer setup and the cited compiler and format behavior, not a universal best practice.

## Practical review questions

1. What decision does the name describe? Can a reader select it without seeing its current value?
2. Which appearances and interaction states use it? Are the corresponding foreground and ground roles checked together?
3. Does a utility need it? If so, is its Tailwind namespace correct, and does an alias need `@theme inline`?
4. Does another use share *intent* or merely a current value? Would those uses change together?
5. Is it a shared role, component-local geometry, a recipe, or behavior that belongs in a component?
6. Does it preserve ADR-0038's surface, edge, and shadow rules?
7. If renamed or removed, where are all CSS, utility-class, and JavaScript readers, and what replaces them?

These questions are the proposed Argo governance rule, not claims from any external standard. A reviewable architecture is one in which a contributor can answer them without inventing a new token family for each screen.

## Limits of this research

- The DTCG 2025.10 reports are stable Community Group reports but not W3C Standards; this note does not assume every design tool or generator implements their full resolver. [DTCG reports index](https://www.designtokens.org/technical-reports/).
- First-party systems show patterns at a much larger scale than Argo. Their three-tier diagrams are evidence of possible organization, not measured proof that Argo needs three tiers now.
- This note did not measure Argo's current token use, validate every CSS variable reference, or run light/dark visual captures. Those checks belong to the implementation and review work.
